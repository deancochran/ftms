# Capability conformance corpus v1

This separate, language-neutral corpus tests the static rules in
[`shared/protocol/capability-discovery.md`](../../protocol/capability-discovery.md).
It does not change `../v1/`'s codec schema, vectors, comparison semantics, or npm
exports. It establishes regression evidence, **not** permission to control a
machine, GATT/CCCD completeness, BLE interoperability, PTS, or qualification.

## Identity and accounting

`schemaVersion: 1` and `urn:ftms:capabilities:conformance:v1` identify this fixture
format/comparison contract, not FTMS version or a native package version. This
first corpus is unreleased. Its content revision is the exact schema/vectors plus
this README and the capability protocol document. A runner must report Git HEAD,
dirty state, schema version, and SHA-256 of all **four** files; dirty HEAD alone
cannot identify these local bytes. Pin immutable source revisions for consumers.

The specification basis is FTMS 1.0.1 Table 4.1 condition C.7 (erratum E16264),
Tables 4.4 and 4.15, plus ESR11 and EC23224. The explicit `specificationBasis`
string in both JSON assets is part of the pinned corpus content. Expected reports
were authored from those requirements and the explicit conservative static rules,
not generated by invoking a port. No local-only specification text is distributed
here.

There are currently 63 cases: discovery 12, duplicates 3, features 5,
forward-compatibility 2, measurements 7, operations 4, properties 22, ranges 8.
Runners discover counts from the file rather than hard-coding them. Validate
globally unique case IDs, execute every supported case, and report total, passed,
failed, unsupported, skipped, each case's outcome, category counts, and every
non-pass ID/reason. Invalid schema, unresolved template/edit, invalid expanded
snapshot/report, missing driver, or driver failure is a failure, never a pass.
Only a nonempty fully executed run with no failures/unsupported/skipped cases
may report `complete: true`.

## Literal templates and edits

To avoid duplicating the entire 21-operation report for every small scenario,
`snapshots` and `reports` hold **literal**, schema-validated templates. Each case
names an input and an expected template independently, followed by ordered edits.
This is data compression, not a reference implementation or an expected-result
generator: no output is inferred from input, and no protocol code runs to expand
fixtures. Expand from an independent deep copy for each case/side; never mutate
templates or use a port's actual output as expected output.

An edit contains `path`, optional `op` (default `replace`), and `value` except
for `remove`. Path segments are existing object keys or nonnegative array
indices. For **replacement only**, `"*"` selects all array members and a list of
distinct indices selects those members. Continue traversing the remaining path
for each selection. A string key is not a coerced numeric array index.

- `replace`: replace the addressed value(s); empty path replaces the root.
- `append`: append one literal value to the addressed array.
- `remove`: delete the addressed member; removing the root is invalid.

Each edit observes the result of the preceding edit, including shifted array
indices after removal. Nonexistent fields/indices, wrong container types,
unknown templates, duplicate selection indices and unsupported edits are runner
errors. Validate the entire source against `schema.json`, expand, then validate
each input against `$defs/snapshot` and each expected result against `$defs/report`.

## Portable normalized representation

UUID strings are exactly 32 lowercase hex digits in canonical display/network
byte order (e.g. `00002acc00001000800000805f9b34fb`). Payload `bytes` is an even-length
lowercase hex string in wire byte order; `""` is zero bytes. UUID ordering and
payload endianness must not be confused. Input properties retain all 16 supplied
bits. Bytes are empty for non-success reads; reason must be none unless failed.
Successful zero bytes remain a legitimate snapshot input but malformed decoded
evidence for Feature/ranges. API errors such as invalid pointers are tested by
native tests, not fabricated as portable JSON pointers.

Enum values are defined independently of a language's enum representation:

| Field | Values |
| --- | --- |
| discovery | 0 not attempted, 1 partial, 2 complete, 3 failed |
| scope | 0 unknown, 1 present, 2 absent, 3 ambiguous |
| presence | 0 unknown, 1 absent, 2 unique, 3 ambiguous |
| readState | 0 not attempted, 1 success, 2 failed |
| reason | 0 none, 1 generic, 2 security required, 3 unavailable, 4 timeout, 5 disconnected |
| decode | 0 not attempted, 1 valid, 2 malformed, 3 failed |
| declaration | 0 unknown, 1 not supported, 2 supported |
| prerequisite | 0 not applicable, 1 satisfied (static only), 2 incomplete, 3 inconsistent |

Snapshots may carry optional `c7` truth values: 0 unknown, 1 false, 2 true for
caller-owned `bondingSupported` and `featureMayChangeOverLifetime`. Unknown is
not false. The C bridge passes this evidence through the explicit C.7 API.

Known kinds are 0 unknown; 1 Feature; 2 Treadmill; 3 Cross Trainer; 4 Step
Climber; 5 Stair Climber; 6 Rower; 7 Indoor Bike; 8 Training Status; 9 Speed
Range; 10 Inclination Range; 11 Resistance Range; 12 Heart Rate Range; 13 Power
Range; 14 Control Point; 15 Machine Status. Output `presence` has these 16 slots;
slot zero is always unknown, not a count/summary of unrecognized UUIDs.

Every report contains generation, discovery, scope, observationCount,
diagnosticCount, presence, feature, ranges, operations, observations, diagnostics.
The compact tuples below are ordered and have exactly the listed fields:

| Tuple | Fields |
| --- | --- |
| feature | `[presence, decode, inputIndex, machineRaw, targetRaw, machineUnknown, targetUnknown]` |
| range | `[presence, decode, inputIndex, value]` |
| range value | `[kind, minimum, maximum, increment, scaleDivisor, unit]` |
| operation | `[opcode, targetBit, optionalInTable, declaration, prerequisite, reasons]` |
| observation | `[inputIndex, uuid, properties, knownKind, readState, reason, readSize]` |
| diagnostic | `[code, knownKind, inputIndex]` |

An unavailable input index is **JSON `null`**, never a host's integer `SIZE_MAX`.
The C bridge maps `FTMS_CAP_NO_INDEX` to null. Feature raw words are zero unless
valid. Range value is null unless valid; when valid its signed integer numerators
and divisor are exact, not floating-point approximations. Ranges are ordered
speed, inclination, resistance, **heart rate, power**. Kind and unit values are
0 speed/km/h, 1 inclination/percent, 2 resistance/level, 3 heart rate/bpm, 4
power/watts. This order differs from target bits 3 power and 4 heart rate.

Operations are indexed by opcode 0–20, never sorted by feature bit. No-target-bit
is 255; optionalInTable is 1 for wheel (`0x12`) and spin down (`0x13`) and 0
otherwise. Operation reason flags are OR-combined:

| Value | Reason |
| --- | --- |
| `0x001` | Scope unavailable (also accompanies confirmed-absent/not-applicable scope) |
| `0x002` | Discovery incomplete |
| `0x004`, `0x008` | Feature unavailable, invalid |
| `0x010`, `0x020` | Control Point unavailable, invalid |
| `0x040`, `0x080` | Machine Status unavailable, invalid |
| `0x100`, `0x200` | Required range unavailable, invalid |
| `0x400` | C.7 bonding/lifetime evidence insufficient |

Diagnostic codes are 0 scope unavailable; 1 discovery incomplete; 2 discovery
failed; 3 duplicate characteristic; 4 required characteristic missing; 5 required
property missing; 6 excluded property present; 7 read failed; 8 read security
required; 9 malformed bytes; 10 required range missing; 11 scope contradiction;
12 insufficient C.7 evidence.
Ordering is: duplicate known kinds in kind order (first observation index),
scope unavailable/contradiction, discovery state, per-observation properties then
read failure in input order, malformed Feature then ranges in range order,
missing Feature, missing Machine Status when Control Point is observed, missing
Control Point when a known target is declared, missing ranges in target-bit
order. Duplicate bytes are not decoded by selecting a preferred observation.
Outside present scope, only duplicate/scope/discovery diagnostics are derived.

## Exact comparison and current runner

Compare the entire expanded expected report with the normalized **actual library
output**: exact object keys, exact ordered arrays, exact integer/string/null
values and JSON types. Object key order is insignificant. No subset matching,
numeric tolerance, array sorting, hidden ignored fields or defaulted missing
values is allowed. In particular `true` is not integer 1. Raw read bytes stay in
the input snapshot; observation indices and lengths must describe those bytes.

The C package's host-only Python/jsonschema adapter and compiled C driver consume
these canonical files directly. The bridge has a documented host-test bound of
128 observations and 1024 bytes per read; exceeding it fails rather than silently
dropping evidence. Those limits are **not** limits in the library API or shared
schema. Normal C compilation and consumer use require neither Python nor Node.
Other ports may implement their own bridge without depending on C test tooling.
